# 実験プロトコル

言語: [English](../../experiments/protocol.md) | 日本語

Pythonコマンドはuv経由で実行します。追加の依存パッケージが不要なチェックアウトを `uv sync --locked` で準備し、`PYTHONPATH=src uv run --locked python -m skill_evolver ...` を使用してください。コンテナーを使うテストをすべて実行するには、`SKILL_EVOLVER_DOCKER_TESTS=1 PYTHONPATH=src uv run --locked python -m unittest discover -s tests -v` を使用します。このuvプロジェクトはパッケージを編集可能モードでインストールせず、`src` のインポートパスを明示します。CLIコマンドと、必要に応じて行う `uv pip` によるwheelのインストールは、[README](../README.md)を参照してください。

この実装はローカルの実験ハーネスです。同梱の決定論的なモックモデルは、候補の品質に関係なく、Dockerツールで実際に `uppercase` 操作を実行します。合成トークンを集計し、請求額をゼロUSDとして記録するのは、実行を検証するためです。スキルの品質は、実モデルと探索に使わない評価タスクで評価してください。未対応のプロバイダーは、安全を確保するため拒否します。設定可能なOpenAI経路は後述します。フィクスチャに認証情報や実モデルの呼び出しは不要です。

各実行では、設定、ソースのハッシュ、データ分割の定義、モデルとオプション、価格バージョンを `experiment.json` に固定します。ハーネスは元のスキルを読み取り専用として扱い、各試行の前後に確認します。変更するのは候補の本文だけで、フロントマターはバイト単位で保持します。現在のランナーはスキルのテキストだけを配置するため、同梱されたローカルファイルへの参照は、安全を確保するため拒否します。文書内のアンカー参照は検査します。候補の自動インストールや自動適用は行いません。

探索、選択、最終評価の各分割間で、ケースIDとグループIDが重複してはいけません。公開タスクのフィンガープリント（prompt、files、operation、output_paths）が完全一致するケースも、分割をまたいではいけません。意味的にほぼ同じケースは、分割前に同じグループへ割り当ててください。検証が検出するのは完全一致の重複だけです。フィクスチャでは各分割に3ケースを使います。計画中の品質実験では、探索に12ケース、選択に8ケース、最終評価に20ケースを使います。

実験、ケース、グループのIDは、`[A-Za-z0-9][A-Za-z0-9_-]{0,127}` に一致する空でない安全な文字列とします。ジャーナル内の識別子を構築する前に、数値のID、区切り文字、制御文字を拒否します。そのため、受理された異なるケースIDが、文字列への型変換やパスの曖昧さによって衝突することはありません。

Original、sequential、GAには、独立した探索ごとに同じ探索予算、選択予算、最終評価予算を、それぞれ別枠で与えます。探索には、各手法による元のスキルの測定、すべての評価と再試行、費用ゼロで合成する意味的な提案を含めます。実行前に、上限のあるすべてのモデルステップを含め、余裕を見込んだ試行全体のトークン枠を予約し、使用量が判明したら精算します。使用量が不明な場合は、予約枠全体を計上したままにします。モックプロバイダーの金額はゼロで、実モデルの呼び出しは設定されたトークン単価で集計します。

元の候補、現時点の最良候補、エリート、重複候補は、同じ手法・探索内で完了済みの候補・ケース・反復のキャッシュを共有します。手法間や探索間ではキャッシュを共有しません。

予定された評価をすべて完了した候補だけが順位付けの対象です。元の候補の評価が終わる前に予算が尽きた場合、実験は未完了です。実行に未解決の不確実性がなければ、評価済みの元の候補は引き続き選考対象になります。

逐次探索は現時点の最良候補を保持し、共通の順位付け基準で改善した場合にだけ置き換えます。GAは元の候補と変異候補から開始し、トーナメントサイズを2とし、エリートを2候補保持します。対応するセクション同士の交叉を確率0.5で適用し、その後に1回の変異を行います。見出しのない本文では交叉を省略します。個体数、世代数、独立した探索数、シードは設定で固定します。合成による提案は、非公開ケースや正解にアクセスせずに変異の仕組みを検証します。

有効かつ評価を完了したすべての候補は、成功率、実行トークン数、本文の長さの順で順位付けします（完全に同順位の場合は、ハッシュで決定論的に順序を決めます）。すべての手法・探索の上位3候補リストを、選択開始前に固定します。最終ケースを評価する前に、すべての勝者を確定します。選択と最終評価の反復回数は3回、探索は1回です。選択で得た情報は提案に戻しません。インフラエラーは1回再試行しますが、タスクの失敗とタイムアウトはゼロ点のままです。未解決のインフラエラーや結果不確定の試行がある場合、比較は未完了になります。

fsync済みの単一ライターJSONLジャーナルに、予約、結果、精算、合成による提案、固定済みリスト、勝者を記録します。アトミックなスナップショットには、変更不能なマニフェストと候補、完了マーカーを含めます。中断された呼び出しに永続化済みの結果がなければ、予定された識別子を使って結果不確定とします。予約は計上したままとし、その呼び出しは繰り返しません。精算前に永続化済みの結果を復元できた場合は、記録された使用量で精算します。再開時には、永続化済みの結果がない呼び出しを再発行せず、結果不確定とします。再開時も実行ディレクトリと元のスキルを利用できる状態にしてください。

レポートには、すべての試行、ケースの結果、費用、残り予算、候補の系譜、差分を残します。対応のある差分を計算する前に、ケースごとに反復結果を平均します。ブートストラップではグループを一様に復元抽出し、抽出した各グループ内の全ケースを保持して、各ケースを等しく重み付けした平均を計算します（10,000回の抽出、95%区間）。区間は1回の固定された探索を条件としたものです。グループ数が10未満の場合、区間は探索的なものに限られます。ゼロを含む区間は結論が出ないことを示し、同等性を示すものではありません。独立した探索をすべて表示し、探索が1回だけの場合、探索の再現性は未検証のままです。モックのレポートでは常に優越性の主張を控えます。

手法・探索の妥当性は、最終タスクの成功とは別に扱います。固定済みの候補リスト、勝者、完了記録には妥当性のスナップショットを含めますが、レポート生成時にはその要約に頼らず、完全なジャーナルを独立に集約します。

最初のインフラエラーの後、許可された再試行に成功すれば、その予定試行は解決済みになります。インフラエラーの再試行を使い切った場合、探索の呼び出しや提案の結果が不確定な場合、永続化された実行結果のない予約がある場合は、再開後も含めて、その手法・探索は未完了になります。使用量不明の予約は計上したままにします。

未解決の実行上の不確実性がなく予算が尽きた場合、評価済みの元の候補は引き続き選考対象です。探索に不確実性があれば、最終試行が成功し、ブートストラップのグループ数が十分でも、条件付きの改善は報告できません。

試行前に、ランナーは入力設定のフィンガープリントとは独立に、変更不能なDockerイメージIDを解決して実験マニフェストに固定します。再開時にはそのIDを検証して使用する必要があり、可変タグを再解決して代用できません。比較可能な最初の観測環境ハッシュを、順位付け前にアトミックに永続化します。不一致は結果不確定・未完了として記録します。レポートでも、過去のハッシュ混在やランタイムの固定情報の欠落を拒否します。変更不能なイメージIDを持たない過去のマニフェストは、有効な実験として再開できません。その検証結果は過去の記録として残り、新規実行が必要です。

ランナーは作成前に、nonceに対応付けたリソース割り当てをfsync済みジャーナルへ正確に記録し、クリーンアップ後に解放を記録します。マニフェストの同一性を検証した後、オーケストレーションは新たな呼び出しを行う前に、完全なイベント履歴を使い、ランナーの検証済みの復旧処理を実行します。復旧時の所有権とラベルの確認、実行時のストレージ上限、デーモンが強制するリソース寿命は、サンドボックス層の責任です。コアには、ホスト実行や広いプレフィックスによるクリーンアップの代替手段はありません。

## 設定可能な実モデルの経路

対応する実プロバイダーは、標準ライブラリのホスト側ブローカーを介したOpenAI Responsesです。`/v1/responses/input_tokens` で正確な事前確認を行い、生成時にも同じリクエスト構成を使います。両方の役割で、対応モデルIDの明示、空のオプション、ホスト側の `api_key_env`、`count_fee_acknowledged: true` が必要です。正の値で設定した入出力共通のトークン単価と価格バージョンも必須です。検証時に認証情報を読み取ったり、APIを呼び出したりはしません。金額予算は設定したトークン単価に適用されます。単価と予算を決める前に、トークン数カウントのリクエスト料金とプロバイダーの請求を別途確認してください。

実モデルによる候補提案では、ブローカーを呼ぶ前に入力・出力を合わせた枠全体を1回分予約します。GAはまずコード上で対応セクションの交叉を行い（セクションがなければ省略を記録し）、続いて本文の変異を1回依頼します。提案のコンテキストには、変更不能な元のフロントマター、現在の本文または交叉後の本文、任意のドナー本文、探索だけから得た失敗のトランスクリプトを含めます。選択・最終評価の観測結果や期待出力は一切含めません。

無効な変異でも既知の有料使用量を計上し、使用量が不明なら予約枠全体を計上したままにします。候補の正確な結果を選択・評価前に永続化し、再開時は再生成せず再利用します。予期しないプログラミング上の障害は上位へ伝播させ、予約は復旧可能な状態に残します。APIの通信エラーと使用量エラーは、文書化された `ModelError` 契約だけを通じて処理します。

レポートは、設定された両方の役割からモックかどうかを判定します。どちらかの役割がモックなら、処理経路の検証に限るという注記を残します。両方が実モデルのレポートでは、GAとoriginalの差、およびGAとsequentialの差の両区間で下限が正となり、独立したグループが10以上あり、データが完全な場合にだけ、固定されたスキル、モデル、探索における改善を記録します。偽のブローカーを使うテストで、この判定規則を検証します。実APIとの互換性と実モデルの有効性を確かめるには、実験が必要です。
